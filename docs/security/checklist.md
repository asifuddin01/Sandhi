# Security checklist

How each item on the site's security checklist is met. The status column means:

- **Done**: enforced in code and covered by tests.
- **Planned**: scheduled, with the slice named. This list is updated as each slice lands.
- **Owner**: a setting in a hosting service or GitHub, described in [operations.md](operations.md).
- **N/A**: does not apply to this architecture; the reason is given.

| #   | Item                                           | Status  | How                                                                                                                                                                                                                                                                                                                                                                                                             |
| --- | ---------------------------------------------- | ------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | Authentication                                 | Done    | Better Auth with email and password (`lib/auth.ts`). Sessions are opaque tokens stored in the database, not client-side tokens.                                                                                                                                                                                                                                                                                 |
| 2   | Login security                                 | Done    | One neutral message for a wrong email or password; rate limits; suspended accounts cannot start a session; unverified addresses are refused.                                                                                                                                                                                                                                                                    |
| 3   | Session management                             | Done    | Seven-day sessions refreshed daily. Signing out deletes the session. Suspension, password reset, and password change end every other session; people can review and end their own sessions.                                                                                                                                                                                                                     |
| 4   | Admin account security                         | Done    | Admin pages and actions re-check capability on the server, and every staff role needs two-factor authentication: administration sends them to set it up, and admin actions refuse without it (tested by posting a genuine action directly).                                                                                                                                                                     |
| 5   | Authorization and access control               | Done    | One permission matrix (`lib/permissions.ts`), enforced by `requireCapability` on pages and `authorize`/`runAdminAction` in actions.                                                                                                                                                                                                                                                                             |
| 6   | OWASP web application security                 | Done    | Covered by items 18–34 and 69–82.                                                                                                                                                                                                                                                                                                                                                                               |
| 7   | Frontend security                              | Done    | Nonce-based CSP with `strict-dynamic`; React escapes output; no `eval` in production; framing denied.                                                                                                                                                                                                                                                                                                           |
| 8   | Backend security                               | Done    | Every input is validated on the server; errors never reveal internals; services fail closed in production.                                                                                                                                                                                                                                                                                                      |
| 9   | CSRF protection                                | Done    | Server actions check Origin against Host; the public API routes refuse other origins (`lib/forms-http.ts`); Better Auth refuses untrusted origins. Session cookies are `SameSite=Lax`. Tested end to end.                                                                                                                                                                                                       |
| 10  | Rate limiting and brute-force protection       | Done    | Upstash limits: sign-in 10 per 15 minutes per IP and per email; forms, uploads, registration, and search limited. Fails closed in production.                                                                                                                                                                                                                                                                   |
| 11  | Password reset security                        | Done    | One-hour single-use links stored only as SHA-256 hashes; the same answer whether or not the address exists; resetting ends every other session. Replay tested.                                                                                                                                                                                                                                                  |
| 12  | Email verification                             | Done    | Sign-in requires a verified address; invitations verify by possession of the emailed link.                                                                                                                                                                                                                                                                                                                      |
| 13  | Secure account registration                    | Done    | No public sign-up (endpoint removed). Accounts come only from invitations: seven-day tokens stored hashed and claimed atomically.                                                                                                                                                                                                                                                                               |
| 14  | Privilege escalation prevention                | Done    | Role is server-only (`input: false`); nobody changes their own access; only the Owner changes the Owner. Tested by posting harvested server actions directly.                                                                                                                                                                                                                                                   |
| 15  | Multi-factor authentication                    | Done    | Authenticator-app codes (TOTP) with ten single-use backup codes: required for Owner, Admin, and Reviewer, optional for members. Each code works once; five tries per sign-in and a 15-minute lock after ten failures; secrets and backup codes are encrypted with the auth secret. An administrator can reset a lost device (password and name required, audited, emailed).                                     |
| 16  | Passkeys and security keys                     | Done    | WebAuthn passkeys (Better Auth passkey plugin) sign in without a password or code, and require the device to verify the person (fingerprint, face, or PIN), checked on the server too. Adding one needs the password; adding and removing are logged and emailed. Every passkey endpoint is closed over HTTP and reached only through the portal's server actions; production pins the site's origin and RP ID. |
| 17  | Password security                              | Done    | 12–128 characters, hashed with scrypt. New passwords (invitations, resets) found in the Have I Been Pwned corpus are refused; only a five-character SHA-1 prefix leaves the server. If the service is down, the password is allowed and the gap logged.                                                                                                                                                         |
| 18  | Input validation                               | Done    | Zod schemas for public forms and APIs; explicit parsing for admin forms; stored settings validated again when read.                                                                                                                                                                                                                                                                                             |
| 19  | Output encoding and XSS protection             | Done    | React escaping; Markdown through `rehype-sanitize`; JSON-LD escapes `<`; nonce CSP as a second line.                                                                                                                                                                                                                                                                                                            |
| 20  | SQL injection protection                       | Done    | Prisma parameterised queries only; no raw SQL in the application.                                                                                                                                                                                                                                                                                                                                               |
| 21  | Command injection protection                   | Done    | The application never runs shell commands.                                                                                                                                                                                                                                                                                                                                                                      |
| 22  | Path traversal protection                      | Done    | No filesystem access from requests. Storage keys are generated by the server (`applications/pending/<uuid>/…`), never taken from input.                                                                                                                                                                                                                                                                         |
| 23  | SSRF protection                                | Done    | Server-side requests go only to fixed hosts (Turnstile, Upstash, Resend, R2). DOI/arXiv import will use an allowlist of hosts.                                                                                                                                                                                                                                                                                  |
| 24  | File upload security                           | Done    | Signed ten-minute upload URLs to a private bucket; the server verifies a signed receipt, content type, size, and the `%PDF-` signature.                                                                                                                                                                                                                                                                         |
| 25  | API security                                   | Done    | Same-origin checks, validation, rate limits, and generic errors on every endpoint.                                                                                                                                                                                                                                                                                                                              |
| 26  | API authentication and authorization           | Done    | Auth endpoints come from Better Auth with unused ones disabled; admin changes are server actions behind `runAdminAction`.                                                                                                                                                                                                                                                                                       |
| 27  | IDOR / BOLA protection                         | Done    | Records are loaded through capability checks and visibility filters (`lib/visibility.ts`); member actions check who may manage whom.                                                                                                                                                                                                                                                                            |
| 28  | HTTP security headers                          | Done    | `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`, `Permissions-Policy`, and `Cross-Origin-Opener-Policy` on every response.                                                                                                                                                                                                                                                                       |
| 29  | Content Security Policy                        | Done    | Per-request nonce, `strict-dynamic`, no plugins, no framing, restricted `base-uri` and `form-action`. Tested for violations.                                                                                                                                                                                                                                                                                    |
| 30  | HTTPS / TLS security                           | Owner   | Vercel serves HTTPS only; the CSP upgrades insecure requests.                                                                                                                                                                                                                                                                                                                                                   |
| 31  | HSTS protection                                | Done    | Two years, including subdomains, from production builds. Preload is an owner decision.                                                                                                                                                                                                                                                                                                                          |
| 32  | Cookie security                                | Done    | Session cookies are `HttpOnly`, `SameSite=Lax`, and `Secure` with the `__Secure-` prefix over HTTPS.                                                                                                                                                                                                                                                                                                            |
| 33  | CORS security                                  | Done    | No CORS headers are sent, so browsers block cross-origin reads. The R2 bucket's CORS is limited to the site (owner).                                                                                                                                                                                                                                                                                            |
| 34  | JWT / token security                           | Done    | No JWTs for sessions. Invitation and reset tokens are random, expiring, single-use, and stored hashed.                                                                                                                                                                                                                                                                                                          |
| 35  | Secret and API key management                  | Done    | Secrets only in environment variables; `.env*` ignored by git; no secret in the repository's history (checked).                                                                                                                                                                                                                                                                                                 |
| 36  | Environment variable security                  | Done    | Production refuses a short auth secret, a missing site URL, missing rate-limit or Turnstile keys, and an unencrypted database connection.                                                                                                                                                                                                                                                                       |
| 37  | Database security                              | Done    | TLS required in production; a least-privilege role script; append-only audit log.                                                                                                                                                                                                                                                                                                                               |
| 38  | Database access control                        | Owner   | Run `scripts/db/least-privilege.sql` and point `DATABASE_URL` at `sandhi_app` (tested).                                                                                                                                                                                                                                                                                                                         |
| 39  | Database encryption                            | Owner   | Neon encrypts at rest (AES-256).                                                                                                                                                                                                                                                                                                                                                                                |
| 40  | Data encryption at rest                        | Done    | Neon and R2 encrypt at rest; authenticator secrets and backup codes are also encrypted by the application with the auth secret.                                                                                                                                                                                                                                                                                 |
| 41  | Data encryption in transit                     | Done    | HTTPS with HSTS for visitors; TLS required for the production database.                                                                                                                                                                                                                                                                                                                                         |
| 42  | Sensitive data protection                      | Done    | Passwords hashed; tokens hashed; applicant files private behind short signed URLs; member email addresses never public.                                                                                                                                                                                                                                                                                         |
| 43  | Personal information protection                | Done    | Privacy page; minimal collection; applicants' data visible only to Owner and Admin; retention period set in Admin → Settings.                                                                                                                                                                                                                                                                                   |
| 44  | Error handling and information disclosure      | Done    | Generic user-facing errors; the error page shows no message or stack; details go to server logs only.                                                                                                                                                                                                                                                                                                           |
| 45  | Security logging                               | Done    | Sign-ins (device and network, never the full IP address), failed attempts with their reason, rate-limit lockouts, reset requests, password changes, and alerts sent are written to the audit log (`lib/security-events.ts`), alongside every admin change.                                                                                                                                                      |
| 46  | Audit trail / admin activity logging           | Done    | Every admin change is written with its diff in the same transaction; append-only at the database level with the least-privilege role; viewable by Owner and Admin.                                                                                                                                                                                                                                              |
| 47  | Security monitoring and alerts                 | Done    | Account holders are emailed about repeated failed sign-ins, sign-ins from a new device or network, and password changes; the Owner is emailed when someone else grants administrator access. GitHub alerts are covered by items 57–61.                                                                                                                                                                          |
| 48  | Account lockout and suspicious login detection | Done    | After 10 attempts an account's sign-in pauses for 15 minutes (per email and per IP). Five failures within 15 minutes, or a sign-in from an unseen device and network, email the account holder (at most one failed-attempt alert an hour).                                                                                                                                                                      |
| 49  | Bot and automated attack protection            | Done    | Turnstile on public forms (fails closed in production) and rate limits. Vercel bot protection is an owner option.                                                                                                                                                                                                                                                                                               |
| 50  | DDoS protection                                | Owner   | Vercel's automatic mitigation; Attack Challenge Mode when needed.                                                                                                                                                                                                                                                                                                                                               |
| 51  | Web application firewall                       | Owner   | Vercel Firewall rules for `/api/*` and sign-in.                                                                                                                                                                                                                                                                                                                                                                 |

| 53  | File storage security                          | Done    | Private bucket with no public URL; server-generated keys; signed, expiring access.                                                                                                                                                                                                                                                                                                                              |
